# 对话体验修复与外观设置 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 消除后台会话里凭空出现的「新会话 · 草稿」，让 Antigravity 的可重试服务错误不再把整轮标成失败并留下常驻红框，把会话条数与对话区宽度做成设置页可改的产品设置。

**Architecture:** 前端只修状态来源（不再凭队列快照伪造会话视图、后台列表按队列真实待办判定）；服务端把「原生服务临时故障」与「本轮失败」分开判定；外观偏好并入现有 `ProductSettingsSchema`，由已存在的产品设置存储与保存流程承载，不新建第二套存储。

**Tech Stack:** TypeScript、Zod、Zustand、React、Fastify、Vitest。

**Spec:** 本文件「短设计」一节；决定已在对话中逐项确认。

## Global Constraints

- 回复、注释、文档、提交信息一律中文。
- 会话条数默认 **5**，取值 1–20；对话宽度预设 **小 720 / 中 860 / 大 1040**，自定义 480–1400，默认「中」。
- 外观偏好写进 `packages/shared/src/settings/product-settings.ts` 的 `ProductSettingsSchema`；服务端 `createProductSettings` 只透传，不另写字段校验。
- 不新增第三方依赖；不改 `apps/desktop` 打包配置；不升版本号。
- 测试不得写死开发机绝对路径；不放宽既有超时来掩盖竞争。
- 每个任务收尾必须让该任务的测试命令通过，再提交。

## Review Focus

按最可能伤到真实使用者的顺序：

1. 队列快照带的 `conversationId` 已不在内存（删除/归档会话、改项目目录、身份归并之后）→ 后台会话不得新增任何条目。
2. 队列仍有待发项但会话此刻空闲 → 后台会话必须仍能进入，不能因为改判定而丢掉真实待发队列。
3. 同一原生会话的内存视图被归并后，迟到的同 `sessionId` 快照 → 必须挂回存活视图，不得出现两条。
4. 磁盘上的旧 `product-settings.json` 没有 `appearance` 字段 → 必须读成默认 5 与「中」，不得报 `settings_invalid`。
5. ACP `session/prompt` 因 HTTP 524 失败但本轮已产出正文 → 不出现红色错误块，`turn_end.isError` 为 false；没有任何正文时仍必须报错并标记失败。
6. Antigravity 没有用量报告时，上下文面板的文案要说明是原生未报告，不能与「尚未开始」混为一谈。
7. 模型回复里的**裸相对路径链接**（`src/app.ts`、`docs/readme.md`）与自定义协议链接（`vscode:`、盘符）→ 不得显示成 `标签 [blocked]`；`http(s)`、`mailto:`、`#锚点` 仍要是可点链接；`javascript:`/`data:`/`file:` 必须继续保持不可点。

## 短设计

### 为什么

- **幽灵条目**：`applyFollowupSnapshot` 在内存里找不到 `conversationId` 时会用 `emptyConversation` 伪造一个视图写进 `background`；该视图无 `sessionId`、无正文、无草稿，却因 `queueId` 被后台列表长期显示为「新会话 · 草稿」。全仓库只有 `emptyConversation` 会把 `queueId` 置回 `undefined`，所以一旦造出来就不会自行消失。
- **报错粘在每条回复上**：`acp/client.ts` 把含 524 的 JSON-RPC 错误映射成 `AcpError('native')`，`acp/runtime.ts` 的 `catch` 无条件发出 `error` 事件 + `turn_end.isError = true`。agy 的网关在长回复末尾返回 524 是常态，正文其实已经流完，于是每条回复后面都跟着一条红色错误。
- **上下文用量空态**：文案对所有 CLI 一律说「此会话尚无可用的上下文用量与窗口报告」，看不出是原生没报，还是应用没接。
- **回复里的 `[blocked]`**：不是模型输出，也不是原生协议字段。`rehype-harden`（Streamdown 的默认 rehype 插件，配置里 `defaultOrigin: undefined`）遇到无法用 `new URL(url)` 解析的链接会把它替换成 `<span>` 并在文字后插入文本 `" [blocked]"`。实测：`[src/app.ts](src/app.ts)`、`[x](docs/readme.md)`、`[x](package.json)`、`[x](vscode://...)`、`[x](C:\path)` 都会被追加；`https:`、`mailto:`、`#锚点`、`./x`、`/x` 不受影响。agy 回复里大量出现仓库内文件引用，于是每条回复都带出这种标记。安全策略本身要保留（`javascript:`/`data:`/`file:` 必须继续拦），错的是「正常但不可解析」的链接被降级成了噪声。

### 怎么做（已确认）

| 点 | 决定 |
| --- | --- |
| 幽灵条目 | 快照找不到视图就丢弃，不伪造；后台列表从「有 queueId」改为「队列仍有未完成项」 |
| 报错 | 服务型诊断（524/500/503）在已产出正文时降级为可折叠记录且 `isError:false`；无正文或非服务型错误照旧报错 |
| 报错兜底 | 时间线里的错误条目可手动关闭 |
| 上下文文案 | 按 CLI 区分，Antigravity 说明是原生未报告 |
| 回复里的 `[blocked]` | 渲染层安全策略误伤：在 Markdown 解析阶段把不可渲染的链接降级为纯文本，不放宽安全策略 |
| 条数 | 默认 5，可调 1–20，放在设置页「通用设置」 |
| 宽度 | 小/中/大/自定义，共用 `--conversation-width` 变量，放在设置页「通用设置」 |
| 存储 | 两项都进服务端产品设置（新增 `appearance` 段） |

### 非目标

- 不重做时间线的流式渲染：现有的 delta → `Streamdown` 流式路径是正常的，本次不动。
- 不改侧栏拖拽宽度等本机界面偏好（仍在 localStorage）。
- 不为旧数据集写迁移脚本，`appearance` 缺失由 Zod 默认值补齐。

/** 快照只能挂到已存在的视图；同原生会话的身份可以跨 conversationId 认领。 */
function knownView(state: ChatState, snapshot: FollowupSnapshot): ConversationView | undefined {
  const byId = conversationById(state, snapshot.conversationId);
  if (byId || !snapshot.sessionId) return byId;
  return conversationViews(state).find(
    (view) =>
      view.workspaceId === snapshot.workspaceId &&
      view.agent === snapshot.agent &&
      view.sessionId === snapshot.sessionId,
  );
}

- [ ] **Step 3: 实现暂存与兜底**

`adapter.ts`：

```ts
private pendingService?: Extract<AgentEvent, { type: 'error' }>;

private diagnostic(line: string): void {
  const event = antigravityDiagnostic(line);
  // 服务型故障先暂存：原生可能已自行重试成功，本轮结束前不写成永久错误。
  if (event?.type === 'error' && serviceFailure(line)) {
    this.pendingService ??= event;
    return;
  }
  this.nativeFailure ||=
    event?.type === 'error' || /^(?:error\s*:|AGY_ERROR\s*:)/i.test(stripVTControlCharacters(line).trim());
  if (event) this.notice(event);
}
```

`finishTurn` 在现有兜底 `notice` 之前插入一行：

```ts
if (isError && this.pendingService) this.notice(this.pendingService);
```

（顺序保证：真实失败时先报出具体服务原因，`reportedError` 已置位，泛化文案不会覆盖它。）
