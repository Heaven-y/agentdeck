# 开发指南

核对日期：2026-11-10。按当前工程组织环境、质量、Git 和验证规则。产品优先级见[路线图](../roadmap.md)，协议边界见[原生对话接入](../engineering/native-dialogue.md)，本地成包见[安装指南](local-installation.md)；旧验收数据及已退役问题通过 `c686ef2` 查询。

## 1. 本机环境

Windows 10/11、Node.js 22+ 与 Git 是开发基础。按需安装 `claude`、`codex`、`agy`；缺少某个 CLI 应只影响对应功能。SQLite 摘要读取使用 Node 内置模块，不要求额外原生绑定；rclone 已不属于依赖。

本机 Python 仅供部分开发技能脚本使用，命令为 `python -X utf8`。服务器分析使用已有解释器和项目环境；本机后端主要协调异步 I/O。

### 1.1 代码规范

- 文件默认 UTF-8/LF；PowerShell 脚本按 `.editorconfig` 使用 UTF-8 BOM，以兼容 Windows PowerShell 5.1；`.slurm` 必须 LF。
- 中文说明与必要注释，函数保持小而可复用，消除重复；不为简单业务堆叠抽象层。
- 外部命令使用参数数组和明确超时/输出限制，避免拼接 shell；涉及敏感值时通过受控 stdin 或环境注入。
- Python 文本 I/O 指定 UTF-8，子进程按需设置 `PYTHONUTF8=1`，不复用系统保留变量名。
- 依赖固定具体版本，优先维护活跃、类型完整、许可兼容的成熟库。运行时使用 MIT/Apache/BSD/ISC 等宽松许可，GPL/AGPL 项目只参考设计；开发工具许可单独记录。
- 安全边界先验证库的真实行为，不满足时保留明确的小范围实现并记录理由。涉及认证、执行或删除时报告验证范围与未知边界。

### 1.3 质量检查

按直接和间接影响范围验证；新产物、全局布局或影响不明时扩大范围。验证通过后，只有新改动、新问题或未解决风险才复验。阶段整合的完整门禁为 `npm run check`，Windows/Linux CI 运行同一入口。

| 检查 | 命令 | 约束 |
|---|---|---|
| 类型 | `npm run typecheck` | shared、server、web、desktop、scripts 全部通过 |
| ESLint | `npm run lint` | 零错误；圈复杂度 ≤10、认知复杂度 ≤15、嵌套 ≤4、参数 ≤4 |
| 格式 | `npm run format:check` | Prettier 无差异；Markdown 保留人工排版 |
| 文档 | `npm run docs:check` | 当前存在的跟踪文档及未忽略新文档；相对链接、锚点、导航与跨文档重复长句检查 |
| 重复率 | `npm run dup` | 50 token 起检测，非测试代码重复率 ≤3% |
| 桌面构建 | `npm run build:desktop` | 构建入口可用，不替代真实窗口验收 |
| 测试覆盖 | `npm run coverage` | 全局行/语句/函数 ≥85%、分支 ≥75%；shared 各项 ≥90%；安全模块行/语句/函数 ≥95%、分支 ≥90% |

文档检查采用 NUL 分隔枚举，保留中文和空格路径；开发技能与过程目录即使意外跟踪也不纳入检查，已删除文件跳过。相同长句跨文件达到 40 字符会报告，单篇超过 600 行只预警。新文档须登记在导航，不为通过检查重复定义参数。

新增或改动用户可见提示时，按[文案规范](../product/ui-layout.md#71-用户可见提示)检查变更实际影响的显示位置，包括前端、服务端错误透传和桌面弹窗。审查先问「不显示会不会妨碍操作」，再核对已知事实、用户下一步和是否重复展示。涉及发送、保存或删除的提示分别对照已成功、明确失败和结果不明，不能把不明写成未执行，也不能为每种内部状态各加一条警告。只验证受影响的场景，不用关键词扫描代替判断。

定向覆盖率可在仓库根目录用测试文件路径筛选，并用 `--coverage.include` 限定生产模块。Vitest 5 使用 `--project` 时会将覆盖匹配根改为对应包；此时不能直接沿用根目录前缀，否则可能得到 0/0 空报告。空报告不作为覆盖验证通过依据。

测试放各包 `tests/`，路径与模块相呼应。只补核心行为和实际回归，用临时目录生成绝对路径，不写开发机固定路径；脚本枚举回归复用服务端 `tests/dev` 发现范围。生命周期测试用明确屏障，不凭放宽超时掩盖竞争。

模拟 Windows 安装的测试须显式提供临时程序入口，避免 Linux 按自身扩展名规则查找；目录符号链接按链接逐项清理。真实进程占用测试只断言本用例启动的进程能被识别并继续响应，空闲与证据不足由受控快照验证，不要求共享 CI 主机上的所有 Node 参数均可还原。Windows CIM 探测的冷启动已测得约 18～26 秒，生产等待上限为 45 秒，并保留取消与外层事务期限。

重构后按目录增加独立聚合门槛（行/语句/函数/分支）：platform、Claude、Codex、chat/sessions 为 90/90/90/80；Antigravity、agents/common、plugins 宿主、web/cli 为 85/85/85/75。shared 与 HTTP 安全模块继续使用原更高门槛，总体门槛仍保留。目录分组能防止一个高覆盖模块掩盖另一个适配器退步，不要求复制相同测试到每一层。

jscpd 递归扫描 server/web/desktop 的 src、shared/src、scripts/dev 与 scripts/packaging，新 CLI、platform、内置插件无需额外登记单文件。仍检查跨目录重复，限制 3%；合理的协议差异不强行抽象成全能基类。构建产物、依赖和测试不计入生产重复率。

覆盖率排除项由根 Vitest 配置统一维护：进程入口、需要真实 SSH 的池、前端组件及特定浏览器封装分别由相应验证覆盖。不得放宽全局门槛；必要的局部 lint 例外写明原因。jsdom 放根开发依赖，组件测试用 Testing Library，普通逻辑使用 Node 环境。

### 1.4 删除一个概念时的闭包

删除跨层概念（字段、模块、路由、视图）不是“删掉定义再加门禁”。门禁只能确认，不能发现：零读者的死代码对类型检查、测试、构建、文档检查全部不可见，`npm run check` 全绿仍可能留着没消费者的 schema、还在校验已删文件的打包脚本、和列着已删路由的文档表。

顺序固定为：

1. **先搜读者**：用概念自身的标识符枚举（字段名、模块名、路由前缀、导出符号、界面文案），记下每一处读者及所在层。
2. **按层改完**：类型读者由 `tsc` 兜底，运行期与打包期读者没有兜底，必须靠第 1 步的清单人工确认。
3. **再搜一次**：目标应为零命中；剩余命中逐条判定是否合法（同名不同义的字段、刻意验证旧值被丢弃的测试）。
4. **最后才跑门禁**。

批量文本替换只对“概念独占的标识符”安全。`server:` 在 MCP 调用里是服务名、在概览里是磁盘采样目录、在终端创建里是目标参数，重载名上的正则会把它们一起删掉，且只在测试失败时才暴露。重载名逐个改，用编辑器而不是脚本。含中文文件的编码陷阱见[第 5 节](#5-按症状查)。

### 1.7 本仓库的 Git 分支与提交

保留 `main`、大功能分支与短期小分支，不增加长期 develop。

| 分支 | 命名 | 生命周期 |
|---|---|---|
| 主线 | `main` | 已整合基线，长期保留；合入不等于发布 |
| 大功能 | `feat/<功能域>` | 一个完整功能域，阶段合入后保留；删除须明确授权 |
| 小功能 | `<类型>/<主题>` | 按实际归属合入功能分支或 main 后清理 |

- 名称用小写英文和连字符，体现主题，不用工具前缀、日期、人名或 wip。
- 开始前检查状态、分支和 worktree 占用；保留别人的未跟踪文件，不用 `git clean` 清理工作区。
- 先判断目标分支：某功能仍在开发，其子功能和修复从所属功能分支创建并合回；功能已交付后的独立修复从 main 创建并合回。不因为改动小就绕过正在开发的功能分支，也不为已交付修复额外经过历史功能分支。
- 提交按可审阅阶段组织，使用 `type(scope): 中文摘要`，代码与对应文档一起；未经明确要求不提交、不推送，当前会话授权持续有效。
- 同一阶段的零散修正与验收说明尽量在提交前合并整理；不同功能或需要独立回退的修复保留独立提交，不把整个开发周期压成一条。
- “按阶段提交”与“每个提交都能独立通过检查”在本仓库会冲突：类型检查跨 workspace 全局执行，拆细后中间提交可能引用已删的 shared 导出而无法通过。遇到这种结构，按可独立验证的边界合并（例如代码与文档分开），并在提交信息里说明合并原因；不要为了凑阶段数留下通不过检查的中间提交。
- 目标分支没有分叉且小分支只有一条有效提交时，可用 `git merge --ff-only`；多条有意义的提交、并行开发或大功能阶段进入 main 时用 `git merge --no-ff`。不能快进时先核对分叉来源，不自动改写目标分支；冲突解决后复验受影响范围。
- 不机械执行“小修复合并一次、大分支立即再合并一次”：仍在开发的修复先整合到所属功能阶段，阶段验收后再进入 main。大功能分支已阶段交付并不表示以后所有修复都必须绕经它。
- 已推送或被他人基于其开发的提交不重写。未推送历史仅在明确授权下整理，先保存完整备份、分支映射和原验收证据，逐阶段验证文件快照等价，并同步迁移后续开发分支。一次性整理记录留在本机，正式文档只保留长期规则；公开历史引用必须能从发布分支访问。
- 没有冲突或新代码的整合沿用可靠验证基线，不重复跑无关全量测试。
- 小分支确认已被目标包含且没有工作树占用后用 `git branch -d` 删除，不用 `-D`；大功能分支不按“已合并”批量清理。
- 只有获推送授权才同步远端，先 fetch 核对真实状态，不把离线的 origin 引用当最新结果；正常推送，禁止强推。
- 推送前先审查待推提交：同一主题反复改的碎片在推送前合并，推送后再发现就只能留在历史里。已经共享的提交不因“看起来不整齐”而重写，如实保留当时的过程。
- 日常任务先在功能分支开发。用户于 2026-11-08 明确允许验证后合入本地 main；推送和发布仍需各自授权。
- 小阶段结束回到所属大功能分支；合入 main 后暂停开发时回到 main。报告保留分支、已清理小分支与是否推送。

2026-10-03 之前的旧合并记录不改写。

### 1.8 文档事实审查

实现者与审查者共用本次行为变更清单，核对方式如下：

1. 从差异提取变化的行为、字段、默认值、入口和生命周期，用标识符及中文别称搜索关联说明，包含未修改的 README、专题文档、示例和代码注释。
2. 每项变化对照当前实现和相关验证，核对用法、配置、接口及状态描述。只修改受影响内容；无需改文档的项目简述理由。
3. 已完成计划按[文档维护规则](../README.md#维护规则)转入历史追溯，当前说明直接描述生效行为。
4. 审查者独立复查关联说明，简报已核对的主题与文件、发现的遗漏及有依据的不适用项。发现遗漏后修正并复核对应范围，再结束任务。

`docs:check` 检查链接、锚点、导航和重复文本，事实一致性由上述审查完成。核对结果写在任务或审查记录中，无需另建文档。

### 2.1 任务流程

仓库已配置工单位置、分流标签和领域文档，无需再运行 `setup-matt-pocock-skills`。

| 场景 | 使用方法 |
|---|---|
| 范围明确的小改动 | 直接做，按受影响场景验证和审查，不为改字或小修复另写规格、拆工单 |
| 大功能或可分阶段的工作 | 重大不确定性用 `grill-with-docs` 澄清，按 `to-spec` → `to-tickets` 写规格、拆成可独立验收的工单，再按顺序实现 |
| 实现和回归 | `implement` 按工单工作；用 `diagnosing-bugs` 建立复现，用 `tdd` 从可观察接口验证核心行为 |
| 交付前审查 | 按 `code-review` 分开核对需求和仓库规范，再按[文档事实审查](#18-文档事实审查)核对相关资料 |
| 架构问题和反复失误 | `improve-codebase-architecture` 先找改动分散的边界；`retro` 从已发生的问题判断应改文档、补验证还是加自动检查 |

工单只写到[本地目录](../agents/issue-tracker.md)；术语、产品要求和设计决策按[领域文档](../agents/domain.md)各归其位。模板要求额外确认、跑全量测试或提交时，按本项目的澄清、验证与 Git 规则执行。

## 3. 启动与隔离验证

| 场景 | 命令 |
|---|---|
| 桌面开发与热更新 | `npm.cmd run dev:desktop` |
| 浏览器热更新 | `npm.cmd run dev` |
| 本机静态托管 | `npm.cmd start` |
| 指定关联测试 | `npm.cmd test -- apps/server/tests/chat/turn-manager.test.ts` |
| 控制台受控夹具 | `node --import tsx scripts/dev/e2e/e2e-console.ts` |
| Windows 本地包 | `npm.cmd run package:desktop` |
| 解包目录与冒烟 | `npm.cmd run package:desktop:dir`，再按本地安装指南运行冒烟检查 |

开发服务地址和环境覆盖项统一见[启动配置](../engineering/architecture.md#53-启动配置)。前端先同源握手，服务重启后需重新取得会话。不要把测试页面指向正在使用的真实配置。

后台验收进程的 stdout/stderr 写入本轮独立日志文件或设为 ignore，不继承可能先退出的工具输出管道。验收结束后关闭自己创建的窗口、进程与端口；桌面日志已处理异步 EPIPE，但这不能代替验收脚本的退出清理。

桌面 `dev` 和 `start` 在运行 electron-vite 前执行 Electron 官方安装器：文件完整时立即返回，缺失时从缓存恢复或下载锁定版本。仅安装 npm 包不一定已包含桌面运行文件，跳过安装脚本或下载中断会使 electron-vite 报 `Electron uninstall`。已有依赖时可在仓库根目录运行 `node node_modules/electron/install.js` 修复，再执行 `npm.cmd run dev:desktop`；无需删除整套 node_modules。首次下载需要网络，未完成下载不能只创建 path.txt 充当成功。

桌面开发使用 electron-vite 的 renderer 服务和监听构建。前端入口复用 web 的 Vite/React/Tailwind 配置，默认页面地址为 `http://127.0.0.1:5173`，API 与 WebSocket 代理到本机后端；Host、Origin、Cookie 和插件 iframe 限制继续生效。

| 保存的内容 | 开发窗口行为 |
|---|---|
| React 页面、组件与 CSS | Vite HMR/Fast Refresh，通常保持当前页面与可保留的组件状态；不重启后端 |
| Electron preload | 重新构建并刷新页面，页面内临时状态可能重置 |
| 后端、桌面主进程及其共享源码 | 重新构建并自动启动新 Electron 进程 |
| 依赖或启动/构建配置 | 按变更安装依赖后停止并重新执行开发命令 |

后端重启会中断本次运行中的模型回合、SSH 通道和终端。不要在真实任务运行时编辑会触发重启的文件；原生历史与工作台已保存数据继续按各自存储规则保留。热更新只适用于源码开发，已生成的安装包和便携包不会随源码变化。

开发代理要求固定后端端口，使用 `AGENTDECK_HOST` 和 `AGENTDECK_PORT`，默认回环端口 4317；桌面热更新不接受端口 0。5173 被占用时明确启动失败，不自动连接其他开发服务，因此不要同时运行浏览器开发与桌面开发。安装版和静态预览仍使用系统分配的端口。

原生配置接线脚本为 `e2e-claude-config.ts` 与 `e2e-agent-config.ts`。Codex 可通过 `--config` 与 `--codex` 指定隔离来源；只有已授权真实模型验证才追加 `--with-model`。复制认证材料必须明确指定、核对源摘要，清理只触及自身副本，不绕过策略拒绝。

原生资源、插件与独立控制台的组件和服务测试使用临时目录、合成运行器或假 SSH 通道。浏览器验证覆盖真实组件布局和键盘操作；终端搜索用本机输出缓冲，不需要连接真实服务器。外部静态插件的样例与权限边界见[插件契约](../engineering/workbench-plugins.md)。

升版本、制作安装包和发布前，确认范围与版本。打包命令生成本地 Windows x64 产物，使用本机 CLI，用户数据独立保存。当前 0.1.2 测试包包含此前源码功能和修复；包内启动、安装和卸载按[本地安装指南](local-installation.md)分别验收。

SSH 验证使用合成服务或授权目标，核对主机信任和凭据流程。当前控制台文件页只读；终端中的真实写操作先预检，结果不明时先核对远端状态。

## 4. 已知开发约束

- Windows 调 npm 使用 `npm.cmd`，避免 PowerShell shim 行为；`python3` 可能指向商店占位程序，脚本用 `python`。
- 后台服务可能随命令宿主退出。验收脚本在同一进程生命周期内启动、检查并用 `try/finally` 清理；`Start-Process` 后台窗口设为 Hidden。
- 已有非 watch 服务正在使用时，不重启它、不覆盖其默认前端产物。使用专用临时 outDir 和匹配版本的隔离后端，避免混版。
- 大于 500 kB 的构建 chunk 提示通过按需加载和实际分析处理，不抬阈值隐藏；jscpd 只发现精确 token 重复，近似逻辑仍需评审。
- Markdown 没有自动排版；纯文档改动检查链接、编号、事实、编码与差异即可，不为文档内容新增单元测试。
- 当前没有独立 Playwright E2E 目录；界面验收用可用浏览器与隔离服务，临时截图和执行记录放 `.scratch/` 或任务临时目录。

## 5. 按症状查

出现下列症状时再读对应位置，不必平时通读。`AGENTS.md` 只放每次都适用的规则，场景性经验集中在这里。

| 症状 | 查哪里 |
|---|---|
| 用户用问句质疑现有功能（“为什么会有 X”“X 还需要吗”） | 本节的「问句即需求」 |
| 门禁全绿但删除的代码还有残留 | [1.4 删除一个概念时的闭包](#14-删除一个概念时的闭包) |
| 批量替换误删了同名字段 | [1.4](#14-删除一个概念时的闭包) 的「重载名」段 |
| 改含中文的文件后出现乱码或 JSX 报错 | 本节的「PowerShell 编码陷阱」 |
| 按阶段拆分提交但中间提交通不过检查 | [1.7](#17-本仓库的-git-分支与提交) 的同名条目 |
| 文档检查报锚点失效 | 改章节编号后同步全仓库引用，`npm run docs:check` 复验 |
| 配置填了却像没生效（窗口、阈值、默认值） | 本节的「配置未生效先查原生边界」 |
| 同一问题修了又出现，或修复不断引出连带问题 | [5.1 同一问题反复修复](#51-同一问题反复修复) |

**问句即需求。** 用户以问句质疑现有功能时，按“X 该不该存在”处理：先查来历，再给移除或保留的结论，不要只解释为什么存在。含义确实不清时先问一句，不选成本更低的那个理解。这条不属于每次必读——只在遇到这类提问时适用。

**配置未生效先查原生边界。** 配置值填了但表现像默认值时，将“选择身份错误、原生回退、历史数据过期、展示取错来源”列为待验证原因，不先选一个解释当结论。排查顺序：

1. 找一个**原生实际生效**的可观测值，不只看我们写入的配置。窗口核对后端实际采用的模型覆盖，并区分总容量、输出预留和轨迹中的当次输入预算；原生 `/context` 的同名覆盖显示也可能有缺陷，不能只凭一个界面下结论。涉及自动压缩时，还须核对同次生成的 checkpoint 策略，不能用面板窗口增大代替触发点验证，也不能把只读管理进程的参数拼到另一轮生成上。
2. 在隔离配置中构造最小对照：一次只改变一个输入，记录版本、实际选择与原始结果，再解释差异。优先采用不会发送模型请求的只读接口及占位密钥的本地模型模拟；路由变化还需核对请求中的推理参数。仅在用户明确授权且确有必要时做真实验收，先在本地验证该 CLI 支持的取证链路，并设置外发次数上限。AGY 此类需进程退出后从同一存储补读的场景，在核对回复、生成与执行关联及所需参数前保留隔离存储；取不到证据就标为未知，不以更大输入代替准确实验。
3. 核对每个入口的识别语义。已验证的 AGY 原生持久值按标签选择，工作台显式选择才按条目键定位；不能因为字符串相同就混用两种身份。标签相同还须比较真实型号与参数，多义选择不能当作“尚未配置”；错传内部键时出现过的回退也不能推定为所有版本的固定规则。
4. 检查同一数据的所有使用者：设置读写、目录发现、启动参数、协议选择、历史展示和缓存。修复后至少覆盖保存读回、默认/显式选择、新建/续聊；有异步更新时补查切换、取消和失败响应，避免只修一处又从另一处复发。
5. 明确证据强度再交付：单测、原生只读参数、真实生成请求、界面渲染各证明不同事实。未知字段保留未知；被实验推翻的假设写明更正，不把它留在当前说明中当事实。本次完整复盘见[模型选择器决策](../engineering/decisions.md#传给原生的选择器必须是原生认得的标识)。

关键教训是**“能跑通”不等于“配置生效”**。静默回退下对话正常、门禁全绿、覆盖不掉，只有拿原生产物做断言才看得见。同类排查还适用于压缩阈值、权限模式、推理档位、自定义地址。

**PowerShell 编码陷阱。** Windows PowerShell 5.1 的 `Get-Content -Raw` 默认按本地代码页读取无 BOM 的 UTF-8，中文会变乱码并打断 JSX 字符串字面量；`Set-Content` 的默认编码也不能当作 UTF-8。含中文的文件一律用编辑器工具改，脚本只用于不含中文的路径。需要脚本回写时按 `.editorconfig` 显式指定编码并回读校验；PowerShell 7 的默认编码不同，不能把 5.1 的问题泛化到所有版本。变量名不区分大小写，不要用 `$pid`、`$home` 等自动变量。

旧 rclone 路径问题、上一代停靠截图及阶段测试数字不再作为当前开发说明；必要时按[历史追溯](../engineering/decisions.md#历史追溯)读取原始记录。

### 5.1 同一问题反复修复

同一症状在宣告修复后再次出现，或者每轮都要补新的共享状态问题时，先复核因果解释和验收目标。已有复盘中的原则要落实到这次执行；仅再写“全面排查”“增加测试”不能决定问题是否解决。AGY 错误跟随和 1M 配置的证据、反例与验收矩阵见[两例复盘](../engineering/incidents/antigravity-repeated-regressions.md)。

1. **重列已经证明与尚未证明的结论。** 写清用户观察到的失败、期望行为、复现条件、已有解释及其证据来源。检查先前是否把“保存成功”“能显示”“能请求”扩大成“运行已采用”；原结论过强就直接更正，保留旧提交供追溯。
2. **找到第一个值或语义改变的位置。** 沿保存、解析、启动、原生执行、报告及缓存追踪同一份数据，逐段标注身份、输入和输出。每个候选原因都应有能支持或推翻它的观察值；先定位断点，再决定修改哪里，不同时堆叠几个猜测性修复。
3. **先验证取证方法，再做最小对照。** 条件允许且能安全复现时，确认旧实现失败、修复后同条件满足预先写明的断言；材料丢失或外部条件受限时，记录无法复现的原因及替代证据的边界。优先用本地响应或只读接口跨过实际出错的位置；确需真实请求时沿用已有明确授权，限定目标、次数及输入，并在转发前记下次数。协议默认值按已核实语义解析，不能把异常缺失吞成成功；保留取证所需的隔离材料，验收脚本不通过自动补发计费请求弥补证据缺失。
4. **修复时列出需要保持的行为。** 除了本次目标，记录这条路径原来继承的默认值、用户显式覆盖、环境来源、身份和资源生命周期。根据下表选择关联反例，不机械跑全部组合。
5. **按证据范围收尾。** 核对原症状、受到影响的保持项和失败路径，更新当前说明并审查未改动的关联文档。仍无证据的部分继续列为未验证；若又复现同症状或必须再换执行机制，回到断点和方案边界重新分析，不沿用上一轮“已经解决”的前提。

| 本次改变了什么 | 至少检查哪些关联行为 |
|---|---|
| 身份翻译、别名或执行路由 | 默认与显式选择、新建与续聊；型号及推理等请求参数；运行报告与预期不一致时如何处理 |
| 启动隔离、临时配置或新增查询前提 | 从原环境能否找到同一程序；未显式覆盖时继承什么；超时、取消、配置清理和错误是否可见 |
| 缓存内容或信任规则 | 缓存键包含哪些决定性输入；旧格式、切换、安装变更及在途结果失效；读取失败与合法空结果分开 |
| 历史记录、累计结果或异常恢复 | 证据是否属于当前会话和回合；实时终态与历史矛盾、恢复缺少后续证据时是否保留失败 |

窗口及压缩类问题尤其需要把总容量、输出预留、生成输入预算、压缩配置上限、实际触发条件分开。AGY 的回复证据先通过原生引用关联生成记录，再按非空执行标识唯一关联执行配置；时间邻近、同名标签或同一配置文件都不能代替关联。其他 CLI 按其实际提供的身份与计量范围验证，缺少可靠字段时保留未知。具体字段及协议边界由[统计说明](../engineering/cli-observability.md)维护。

结束时在任务或审查记录中留下下面五项即可，不另建重复流水：

- 原因与反证：哪个条件导致失败，对照怎样排除了其他解释。
- 生效证据：观察对象、同一次执行的关联方式，以及字段或请求参数的实际结果。
- 保持项与回归：修复改变了哪些约定，哪些相关反例已经验证；检查数量不代替结论。
- 未知与交付范围：模拟、真实请求、满载或触发测试分别覆盖什么；源码、main 与安装包分别处于什么状态。
- 文档事实审查：包含未修改的哪些关联说明、哪些表述已更正，以及尚未覆盖的范围。

新增自动测试只覆盖本次确认的核心失败条件；已通过且未受后续变更影响的检查不再重复。纯文档复盘只做事实、链接和差异核对，不为补经验重新消耗模型额度或运行整套业务测试。
