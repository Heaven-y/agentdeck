# Antigravity 反复修复问题复盘

本页供后续处理类似问题的人和 Agent 使用：先对照已证实的断点与尚未证明的部分，再按[开发指南 5.1](../../guides/dev-environment.md#51-同一问题反复修复)制定本次验收。下文的执行证据限定于所注明的 AGY 版本、模型和样本；当前源码、main 与安装包的交付状态以[路线图](../../roadmap.md)为准。

## 错误提示跟随续接回合

### 观察到什么

用户发现一轮已有完整答复，下面仍出现超时或“累计结果无法确认”的红条；后续继续对话时，同文错误又可能出现。旧回合的真实错误留在原位置、关闭后重读原生历史又出现，与新回合重新发出一条错误事件是不同现象。前者可能是原生历史的正常展示，后者需要核对事件归属，不能只看红条的位置或文本。

一次真实 CLI 对接本机模拟响应的隔离对照中，新输入后的直播步骤完成、响应成功且进程退出 0，续接结果仍含 524；该错误与输入之前多条原生历史错误同文。另有本机三轮失败、成功、再次失败对照。前者没有完整保留 stderr 分类与本轮全部轨迹字段，结果也没有可证明唯一来源的错误身份，因此只保留“成功响应后仍出现同文错误”的观察，不能证明错误确由历史带入，或排除本轮再次发生同文故障。

2026-11-20 更正此前“原生 `result` 是累计口径”的泛化：[官方 headless 文档](https://antigravity.google/docs/cli/headless/)说明每轮发出一个 `result`，回复属于当前轮，累计表列出的是轮数、用量和耗时。适配器应默认将结果归于本轮；旧样本中的归属冲突需要独立复核，不能成为吞掉全部续接错误的规则。

同日用本机 CLI 1.5.12 的新 profile、独立目录、占位密钥与本机 HTTP 模拟响应重新对照：第一轮成功且退出 0；第二轮 524 失败、退出 3，stderr 明确报告 524；第三轮生成完整新答复，却返回与第二轮完全相同的 524 ERROR，退出 0 且 stderr 为空。共 3 次本机模型请求，另有 7 次外部代理请求被拒绝；未改变用户配置、未向远端模型发送请求。stdout、stderr 及本机请求记录保存在忽略目录，复审独立核对了三轮状态、回复有无、stderr 与错误全文相等。这证实该版本存在归属冲突，不证明所有同文错误都来自历史。

随后通过原生 `readTurnTrajectory` 读回同一隔离会话的 8 步：第二轮错误位于步骤 4，第三轮输入为步骤 5，最后公开答复为步骤 7。将真实 stdout/stderr 与该轨迹交给实际适配器和 TurnManager，再分别回放失败、原样续接、空错误正文、不同新错误四种输入；仅原样续接保留未确认，其余均失败。四项待发仍为 queued、队列暂停，进程启动计数均为 1。空正文与不同错误是明确修改的反例，不冒充原生 CLI 实际产物。

新建会话的第一轮没有旧会话的原生历史，因此不应继承其他会话的错误；这不代表新会话不会发生真实超时、认证或权限失败。续接回合也不能仅凭完整回复或退出 0 宣告整轮成功，或因结果文本曾出现过就断定本轮没有失败。

### 已确认原因与上次验收遗漏

| 已确认的技术问题 | 验收遗漏及修正 |
|---|---|
| 遇到历史同文结果时曾仅改成“归属未确认”的错误文案，后续续接仍重复生成错误事件；随后又将所有续接 ERROR 一概降为未知 | 既检查事件类型与界面，也检查当前错误是否被吞掉；没有严格历史匹配或完整本轮证据时保留原生失败 |
| 原生结果缺少可唯一定位来源的错误身份，历史同文不能证明本轮没有同文新故障 | 曾把直播完成、自然退出 0 当作成功证据；应把成功、当前失败与未知归属分别记录 |
| 空错误正文曾仅凭完整答复改为成功，旧工具失败也可能被误作历史回合故障 | 空 ERROR 本身不是恢复证据；历史匹配不使用普通 TOOL_ERROR 或工具输出，纯 429 恢复单独要求严格的同轮证据 |
| 局部错误编号可能在不同会话相同，关闭动作曾跨会话按编号删除 | 核对关闭和重新读取时的所属会话；关闭只改变展示，不能修改原生历史 |

追溯时可对照 `3f3b1a6` 中的累计错误校正和 `067300d` 中的保守归属修订：后者避免无证据地改判成功，但仍以错误事件承载“未确认”，因而没有消除后续重复红条。

本轮收紧为：默认保留原生 `ERROR`；只有自然退出 0、可信本轮完整轨迹与输入前结构化同文错误同时成立，且无明确当前失败时，才保留结果未确认，不产生本轮错误条，也不改成功或放行待发。说明保留在对应轮次详情，实际暂停在待发区说明并提供“查看原因”，移除常驻页脚。直播正文不等于整轮成功；证据不足时不拿错误结果中的 `response` 补正文。读取失败、缺边界、未完成、异常退出或没有相同旧错误均保留失败；具体条件及同轮纯 429 恢复例外见[原生对话](../native-dialogue.md#headless-回合结果)。

### 对照矩阵：运行结果与用户界面

| 场景 | 原生运行或离线证据 | 应核对的界面和行为 |
|---|---|---|
| 新会话第一轮 | 没有旧会话的历史；本轮仍可能失败。合成核心测试覆盖本轮 524 | 不显示其他会话的旧错误；本轮明确失败时显示对应错误 |
| 旧错误后续接，输入前有结构化同文错误且本轮完整轨迹可信 | 1.5.12 本机模拟重现完整新回复、退出 0、空 stderr 与历史同文 ERROR；适配器分类另用可信轨迹核对 | 自然退出 0 且无当前失败时保留未确认；说明在所属轮次详情，有待发时说明暂停并可查看原因，不自动发送 |
| 续接时又发生真实当前错误 | 合成回放分别覆盖 result 前后 stderr 524、轨迹内 524、权限拒绝与非零退出 | 保留可归属本轮的诊断；不能把明确失败变成成功或中性提示 |
| 没有相同旧错误，或相同文字只来自工具输出或普通 TOOL_ERROR | 本轮离线反例确认旧实现会吞掉真实 result 错误；历史候选已收紧 | 保留原生失败及具体脱敏原因；不能仅因续接或文字相同改为未确认 |
| 读取失败、缺页、身份或输入边界不符、轨迹未完成 | 只读夹具和关联管理测试分别核对读取与完整性边界 | 保留原生 ERROR；不拿错误结果正文补回复、不虚构整轮统计，待发暂停 |
| 空 ERROR 与纯 429 | 旧实现对缺失、null、空白错误正文可仅凭完整答复改成功；本轮已收紧此例外 | 只有严格同轮纯 429 后的完整答复及自然退出 0 可确认恢复；空正文、混合错误或无429证据仍失败 |
| 查看旧轮、切换会话、关闭与重读 | 原生只保存自身历史；工作台未确认状态没有原生持久化契约 | 旧错误留在所属历史位置，关闭仅影响该视图；切换和重读不得串改其他会话 |

离线回放使用脱敏字段、合成事件和模拟进程，不调用真实模型或原生 CLI；本轮独立反例还覆盖旧工具错误误匹配及通用诊断盖住具体 524。它们用于核对适配器分支，不替代新实现的真实 CLI 或界面运行验收，最终验证结果见路线图。旧现场未保存完整收尾证据，不能将全部红条追认为同一原因。

### 实时与重读一致性复查（2026-11-23）

- 本地对照复现了两个不同断点：实时先发暂存的 429，盖过最终明确错误；历史逐条投影可见错误步骤，同一轮会重复显示。把一个限流改成一条更具体的文案不能修复优先级。运行、复核和历史现共用已知原因分类；历史翻页后按同一轮结算。
- 除额度外，对照包含地区、认证、权限、模式不可用、500/503/524，以及临时 `UNAVAILABLE` 后完成、工具自己的 524、纯 429 后完成及未完成的反例。启动与断线等运行期错误未被原生保存时，重开不会凭空生成一条；不把旧轮同文错误转归本轮。Codex 原生失败已与重读对齐；Claude Code 的传输报错没有对应的原生记录时仍只在运行时出现。
- 本机 1.5.14 使用已有的工作台网络配置：一次对照在端口就绪时读不到邮箱，等同一个原生列表返回后读到；另两次跳过早期查询，列表返回后首次即有邮箱。改用单次账号读取后，真实只读入口三次均取得邮箱。没有发模型请求或改登录状态；未把样本时延当作其他版本的保证。

## 1M 配置与实际生成窗口

### 观察到什么

用户设置 1M 后，界面或配置读回能显示 1M，但部分原生执行仍使用约 256K 的输入预算和 checkpoint 配置。用户要验证的是配置在实际生成与压缩策略中是否生效，不能把设置成功、面板显示或一次短请求成功当成同一个结论。

在已核对的 AGY 1.5.9 High 本机对照中，同一 1M 自定义条目的原有标签与内置显示名碰撞：原生 planner 走内置模型且未载入自定义覆盖，输入预算及 checkpoint 上限均为 256,000。使用唯一临时标签后，才进入自定义模型路径并载入 1,000,000 的模型覆盖，对应预算和 checkpoint 上限为 934,464。这是该版本、型号和对照条件下的证据，不倒推其他历史回合或所有模型。

一次已授权的裸 Argon 真实短请求将成功回复、生成记录与唯一执行记录关联，同轮确认 `customModelInfoOverride.maxTokens=1000000`、`contextWindowMetadata.maxContextTokens=934464` 和 `checkpointConfig.maxTokenLimit=934464`，模型输出上限为 65,536。请求输入量约 1.2 万 token，没有达到该配置上限，也没有观察到该轮自动压缩触发。934,464 是该次记录的输入预算及 checkpoint 配置上限，不能写成实际触发点，更不能据此承诺服务支持填满 1M。其他短阈值或历史压缩观察不能拼接成这次真实请求的证据。

### 已确认原因与上次验收遗漏

| 已确认的技术问题 | 验收遗漏及修正 |
|---|---|
| 工作台资源条目键、原生选择 `label` 和服务 `modelName` 曾混用；同一字符串也可能同时是不同条目的键和标签 | 以前只检查某个入口输出了预期字符串，没有逐层核对其来源和原生解释；要覆盖默认选择、显式选择和续接 |
| 自定义标签与内置名碰撞时，即使配置声明 1M，原生仍可能选中内置 profile | 早先只核对保存、目录和 `/context`；须关联同次成功回复、生成与执行记录，读取 planner 覆盖及 checkpoint 配置 |
| 改用临时唯一标签会改变原生选择路径，也可能改变默认推理强度 | 不能只验窗口；同一请求还须对照型号、默认强度、显式覆盖和续接，避免新修复带来新的行为变化 |
| 旧缓存、显示名称与运行报告可能采用不同来源 | 重开菜单、切换会话、旧缓存失效与原生报告不匹配都要单独核对；未知时不能补上预期窗口冒充实值 |

已有复盘曾要求核查原生参数，却没有在当次执行中明确同轮身份、观察字段和成功断言；旧解释还把重名现象收窄为显示问题，后来的 planner 对照证明存在执行选择碰撞。这是证据链与验收范围上的具体遗漏，不推测人员动机或把所有关联缺陷归为同一个根因。更详细的取舍与历史锚点见[设计决策](../decisions.md#传给原生的选择器必须是原生认得的标识)。

### 对照矩阵：实际运行与用户界面

| 断言或场景 | 实际运行证据 | 用户界面应核对什么 |
|---|---|---|
| 配置保存和显示 | 保存、读回和原生目录能证明对应元数据存在，不能证明 planner 采用 | 设置值、菜单选择、显示名称、当前窗口及切换后重开一致；运行时报告不符则显示未知 |
| 旧 High 同名对照 | 本机受控请求进入内置路径，无 1M 覆盖，预算和 checkpoint 上限 256,000；这是失败反例 | 即使面板显示 1M，也不能据此标记实际生成通过 |
| 唯一标签与 1M 覆盖 | 本机模拟及一次真实裸 Argon 请求有同轮关联，模型覆盖 1,000,000，两个已记录上限各为 934,464 | 当前选择应对应实际型号与窗口；同轮运行证据与显示应分别记录，不能由一侧推定另一侧 |
| High、Medium、Low 与显式强度 | 三档及显式覆盖有零外发生产路径模拟；不是各变体的真实服务验收 | 默认强度、用户显式选择、新建及续接结果保持一致，重开菜单不变成其他条目 |
| 满窗口与自动压缩触发 | 真实短请求未压满，也未观察该轮压缩触发；精确触发条件和服务满窗口承载未知 | 不以显示的 1M 或配置上限宣称满载通过或实际触发时刻 |

## 下次遇到类似问题时

按[开发指南 5.1](../../guides/dev-environment.md#51-同一问题反复修复)执行，至少留下以下可复查的结果：

1. 写出用户看到的现象、期望结果及失败/成功/未知三种判定；保留能推翻当前解释的反例，不把上次“已修复”当成前提。
2. 对齐同一个身份与生命周期。错误问题核对会话、输入边界、事件、完整轨迹和退出；模型问题核对资源键、原生标签、服务型号、启动参数、planner 和同次生成、执行记录。
3. 先用隔离本地响应、只读数据或合成事件验证取证链路和失败反例，再按需使用用户已明确授权且次数受限的真实请求。发出前记录预算；缺失证据不自动补发。没有可靠隔离方案时不要复制含用户正文的数据作为试验材料。
4. 把实际运行与用户界面并列验收：检查新建、续接、同轮失败、恢复、切换和重读；选择链还检查默认值、显式值、临时配置、缓存与推理参数。按改动范围选必要组合，明确哪些只是模拟。
5. 对照成功、失败、未知逐项记证据和限制，更新关联文档及未修改说明的事实审查；记录源码、main 和安装包各自的状态。不为得到完整结论，把独立样本、不同模型或不同时刻的数据拼成同一次运行。
