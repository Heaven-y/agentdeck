# Antigravity 反复修复问题复盘

本页供后续处理类似问题的人和 Agent 使用：先对照已证实的断点与尚未证明的部分，再按[开发指南 5.1](../../guides/dev-environment.md#51-同一问题反复修复)制定本次验收。下文的执行证据限定于所注明的 AGY 版本、模型和样本；当前源码、main 与安装包的交付状态以[路线图](../../roadmap.md)为准。

## 错误提示跟随续接回合

### 观察到什么

用户发现一轮已有完整答复，下面仍出现超时或“累计结果无法确认”的红条；后续继续对话时，累计错误又可能出现。旧回合的真实错误留在原位置、关闭后重读原生历史又出现，与新回合重新发出一条错误事件是不同现象。前者可能是原生历史的正常展示，后者需要核对事件归属，不能只看红条的位置或文本。

原生 `result` 是累计口径。一次真实 CLI 对接本机模拟响应的隔离对照中，新输入后的直播步骤完成、响应成功且进程退出 0，续接结果仍含 524；该错误与输入之前多条原生历史错误同文。另有本机三轮失败、成功、再次失败对照。前者没有完整保留 stderr 分类与本轮全部轨迹字段，结果也没有可证明唯一来源的错误身份：它能证明历史错误可能留在累计结果里，不能证明新反馈中的每次 524 都是历史错误，或排除本轮再次出现同文故障。

新建会话的第一轮没有旧会话的原生历史，因此不应继承其他会话的累计错误；这不代表新会话不会发生真实超时、认证或权限失败。只有结果包含未知归属错误的续接回合，不应仅凭完整回复或退出 0 宣告整轮成功。后续再次续接时，原生仍可能返回累计错误。

### 已确认原因与上次验收遗漏

| 已确认的技术问题 | 验收遗漏及修正 |
|---|---|
| 将累计 `result.ERROR` 当作当前回合错误，后续续接再次收到该结果时又生成错误事件 | 只核对错误文案是否变成“归属未确认”不够；还要检查事件类型、对应回合和用户实际看到的红条 |
| 原生结果缺少可唯一定位来源的错误身份，历史同文不能证明本轮没有同文新故障 | 曾把直播完成、自然退出 0 当作成功证据；应把成功、当前失败与未知归属分别记录 |
| 局部错误编号可能在不同会话相同，关闭动作曾跨会话按编号删除 | 核对关闭和重新读取时的所属会话；关闭只改变展示，不能修改原生历史 |

追溯时可对照 `3f3b1a6` 中的累计错误校正和 `067300d` 中的保守归属修订：后者避免无证据地改判成功，但仍以错误事件承载“未确认”，因而没有消除后续重复红条。

本轮修复的目标是：仅累计结果可见且无法归属时保留原生结果未确认，不产生本轮错误条，待发暂停；独立证据确认本轮失败时保留相应诊断。直播正文不等于整轮成功；无可靠的本轮回复证据时不拿累计 `result.response` 补正文。只读复核需校验同一会话、目录、输入边界、完整轨迹及空闲状态，缺少证据不猜测。具体条件、纯 429 恢复及空 `ERROR` 例外见[原生对话](../native-dialogue.md#4-接口与实现选择)。

### 对照矩阵：运行结果与用户界面

| 场景 | 原生运行或离线证据 | 应核对的界面和行为 |
|---|---|---|
| 新会话第一轮 | 没有旧会话的累计历史；本轮仍可能失败。合成核心测试覆盖本轮 524 | 不显示其他会话的旧错误；本轮明确失败时显示对应错误 |
| 旧错误后续接，只有累计 `ERROR` | 真实 CLI、本机响应对照观察到已完成回复和退出 0 后仍有历史同文 524；当前 524 与通用错误两例另经合成事件离线回放 | 不新增本轮红条；在该轮轨迹和当前页脚提示结果未确认，待发不自动发送 |
| 续接时又发生真实当前错误 | 合成回放分别覆盖 result 前后 stderr 524、轨迹内 524、权限拒绝与非零退出 | 保留可归属本轮的诊断；不能把明确失败变成成功或中性提示 |
| 续接时缺页、身份或输入边界不符 | 离线回放覆盖身份不符及无直播正文的情况；分页等条件需由相应管理测试分别核对 | 不把累计正文冒充当前回复，不虚构整轮统计；状态与待发按证据保守处理 |
| 查看旧轮、切换会话、关闭与重读 | 原生只保存自身历史；工作台未确认状态没有原生持久化契约 | 旧错误留在所属历史位置，关闭仅影响该视图；切换和重读不得串改其他会话 |

以上离线回放使用脱敏记录的字段与合成事件、模拟进程，执行期间未调用真实网络或子进程；它不替代新的真实 CLI 或界面运行验收。旧现场未保存完整收尾证据，不能将全部红条追认为同一原因。

## 1M 配置与实际生成窗口

### 观察到什么

用户设置 1M 后，界面或配置读回能显示 1M，但部分原生执行仍使用约 256K 的输入预算和 checkpoint 配置。用户要验证的是配置在实际生成与压缩策略中是否生效，不能把设置成功、面板显示或一次短请求成功当成同一个结论。

在已核对的 AGY 1.5.9 High 本机对照中，同一 1M 自定义条目的原有标签与内置显示名碰撞：原生 planner 走内置模型且未载入自定义覆盖，输入预算及 checkpoint 上限均为 256,000。使用唯一临时标签后，才进入自定义模型路径并载入 1,000,000 的模型覆盖，对应预算和 checkpoint 上限为 934,464。这是该版本、型号和对照条件下的证据，不倒推其他历史回合或所有模型。

一次已授权的裸 Argon 真实短请求将成功回复、生成记录与唯一执行记录关联，同轮确认 `customModelInfoOverride.maxTokens=1000000`、`contextWindowMetadata.maxContextTokens=934464` 和 `checkpointConfig.maxTokenLimit=934464`，模型输出上限为 65,536。请求输入量约 1.2 万 token，没有达到该配置上限，也没有观察到该轮自动压缩触发。934,464 是该次记录的输入预算及 checkpoint 配置上限，不能写成实际触发点，更不能据此承诺服务支持填满 1M。其他短阈值或历史压缩观察不能拼接成这次真实请求的证据。

### 已确认原因与上次验收遗漏

| 已确认的技术问题 | 验收遗漏及修正 |
|---|---|
| 工作台资源条目键、原生选择 `label` 和服务 `modelName` 曾混用；同一字符串也可能同时是不同条目的键和标签 | 以前只检查某个入口输出了预期字符串，没有逐层核对其来源和原生解释；要覆盖默认选择、显式选择和续接 |
| 自定义标签与内置名碰撞时，即使配置声明 1M，原生仍可能选中内置 profile | 早先只核对保存、目录和 `/context`；须关联同次成功回复、生成与执行记录，读取 planner 覆盖及 checkpoint 配置 |
| 改用临时唯一标签会改变原生选择路径，也可能改变默认推理强度 | 不能只验窗口；同一请求还须对照型号、默认强度、显式覆盖和续接，避免新修复带来新的行为变化 |
| 旧缓存、显示名称与运行报告可能采用不同来源 | 重开菜单、切换会话、旧缓存失效与原生报告不匹配都要单独核对；未知时不能补上预期窗口冒充实值 |

已有复盘曾要求核查原生参数，却没有在当次执行中明确同轮身份、观察字段和成功断言；旧解释还把重名现象收窄为显示问题，后来的 planner 对照证明存在执行选择碰撞。这是证据链与验收范围上的具体遗漏，不推测人员动机或把所有关联缺陷归为同一个根因。更详细的取舍与历史锚点见[设计决策](../decisions.md#传给原生的选择器必须是原生认得的标识)。

### 对照矩阵：实际运行与用户界面

| 断言或场景 | 实际运行证据 | 用户界面应核对什么 |
|---|---|---|
| 配置保存和显示 | 保存、读回和原生目录能证明对应元数据存在，不能证明 planner 采用 | 设置值、菜单选择、显示名称、当前窗口及切换后重开一致；运行时报告不符则显示未知 |
| 旧 High 同名对照 | 本机受控请求进入内置路径，无 1M 覆盖，预算和 checkpoint 上限 256,000；这是失败反例 | 即使面板显示 1M，也不能据此标记实际生成通过 |
| 唯一标签与 1M 覆盖 | 本机模拟及一次真实裸 Argon 请求有同轮关联，模型覆盖 1,000,000，两个已记录上限各为 934,464 | 当前选择应对应实际型号与窗口；同轮运行证据与显示应分别记录，不能由一侧推定另一侧 |
| High、Medium、Low 与显式强度 | 三档及显式覆盖有零外发生产路径模拟；不是各变体的真实服务验收 | 默认强度、用户显式选择、新建及续接结果保持一致，重开菜单不变成其他条目 |
| 满窗口与自动压缩触发 | 真实短请求未压满，也未观察该轮压缩触发；精确触发条件和服务满窗口承载未知 | 不以显示的 1M 或配置上限宣称满载通过或实际触发时刻 |

## 下次遇到类似问题时

按[开发指南 5.1](../../guides/dev-environment.md#51-同一问题反复修复)执行，至少留下以下可复查的结果：

1. 写出用户看到的现象、期望结果及失败/成功/未知三种判定；保留能推翻当前解释的反例，不把上次“已修复”当成前提。
2. 对齐同一个身份与生命周期。错误问题核对会话、输入边界、事件、完整轨迹和退出；模型问题核对资源键、原生标签、服务型号、启动参数、planner 和同次生成、执行记录。
3. 先用隔离本地响应、只读数据或合成事件验证取证链路和失败反例，再按需使用用户已明确授权且次数受限的真实请求。发出前记录预算；缺失证据不自动补发。没有可靠隔离方案时不要复制含用户正文的数据作为试验材料。
4. 把实际运行与用户界面并列验收：检查新建、续接、同轮失败、恢复、切换和重读；选择链还检查默认值、显式值、临时配置、缓存与推理参数。按改动范围选必要组合，明确哪些只是模拟。
5. 对照成功、失败、未知逐项记证据和限制，更新关联文档及未修改说明的事实审查；记录源码、main 和安装包各自的状态。不为得到完整结论，把独立样本、不同模型或不同时刻的数据拼成同一次运行。
